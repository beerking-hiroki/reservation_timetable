# reservation_timetable
 
## 1. サービス概要
 
このサービスは、カラオケなどの時間利用の店で、繁忙時にフロントを回すスタッフのための、予約・ウォークイン管理システムです。
ルーム×時間のタイムテーブルで空きを見ながら、受付をしていても、ウォークインや予約をさっと入力できます。
予約の重複を減らし、欲しい人数の予約だけを受け付けられるので、お客様の不満を減らし、売り上げを伸ばせます。
 
---
 
## 2. このアイデアはどこから生まれたか
 
### 2-1. きっかけとなった体験・感情
 
2026年10月末、13時〜16時ごろのピーク帯に、カラオケ店で勤務していたときの体験です。
 
予約が次々と入る一方で来店も多く、予約も来店も、タイムテーブルに入力する時間がほとんど取れませんでした。
 
この時間帯は1名利用をお断りして2名以上で枠を使いたいと考えていましたが、タイムテーブル上で枠をブロックする時間も取れず、1名の予約が入ってしまいました。その結果、本来2名以上で入れたかった枠がいくつか埋まってしまいました。1名の予約は30分などの低単価になりやすく、売り上げを逃すことにもなりました。
 
そのとき「もっと早く対応できていれば、その分の売り上げは増やせたはずだ」と、悔しさともったいなさを強く感じました。
 
### 2-2. なぜそれが「気になった」のか
 
売り上げを上げることが私の仕事であり、予約システムは「予約を受け付けるだけのもの」ではなく「売り上げを伸ばすための道具」だと考えていました。
 
予約枠を調整して、欲しい部屋に欲しい人数の予約を取ることが、予約システムを活用すればできると実感していたからです。たとえば、定員1〜3名の部屋は1名の予約も入ってしまうため、受付を2〜3名の枠に変えたり、別の部屋の2〜3名の予約をその部屋に入れて、1名で取れないようにしたりしました。
 
この調整は、部屋の定員が大きいほど効果的でした。たとえば中団体(4〜6名)を取りたいときは、その人数の枠だけを開けておくことで、その人数の予約だけを受け入れられ、売り上げが大きく伸びました。
 
こうすると、繁忙時間帯に1名・1時間などの利用で満室になることが減り、希望の人数の予約を受けられるので単価も上がりました。だからこそ、この調整ができずに売り上げを逃したことが、強く気になりました。

## 3. 課題の整理
 
### 3-1. 表に見えている困りごと
 
本当に忙しいときは、来店したお客様をタイムテーブルに入力するのが間に合わず、予約がダブルブッキングしてしまうことがあります。その結果、予約時間に来店されたお客様に、待っていただくことしかできませんでした。
 
### 3-2. 本当に解決したい課題は何か
 
**①②に共通する原因**:予約管理の手順が多く、繁忙時に入力や枠の調整が追いつかないこと。
 
**課題①:予約の重複**
- なぜ困る?:最後の1部屋を受付してからウォークインを入力するまでの間に予約が入ると、その予約を受けるしかなくなる。電話番号は登録されていても、相手が出ないことが多く、結局そのお客様が来店してしまう。
- なぜ困る?:予約のお客様を待たせることになり、満足度が下がる。わざわざ予約してくれたのに、約束の時間に利用できないのは、とても不満に感じるはずだから。
- なぜ困る?:満足度が低いと、予約やリピートをしてもらえなくなり、売り上げも下がる。
- → 忙しいときでも、お客様との予約の約束を守れず、信頼を失ってしまうこと。

**課題②:高単価の予約の取りこぼし**
1. なぜ困る?:高単価の予約は人数が多く、お酒を飲む大人も多い。利用料金だけでなく、飲食の注文の機会も丸ごと逃す。
2. なぜ困る?:それが続くと「予約が取れない店」と思われ、他の店に行かれてしまう。
3. なぜ困る?:予約で来てもらえないと、多くの人にお店を体験してもらうチャンスを逃してしまう。
4. なぜ困る?:売り上げが下がると、予算が減り、活気が落ち、シフトも減って人手が足りなくなる。クオリティを保てず、お店が荒れていく。
- → 繁忙時に低単価の予約で枠が埋まり、高単価の予約を逃し続けることで、お客様が離れ、お店の活気と質が下がっていくこと。

## 4. 想定ユーザーについて
 
### 4-1. 想定しているユーザー
 
繁忙時のフロントで、予約管理と受付をまとめて担当するスタッフ。
 
- **年齢**:28歳前後(20代後半)
  - **理由**:売り上げを考えながら現場を回す能力が身につき、その役割を任されている人が、この年代に多いから。
- **生活・状況**:4人で現場を回していて、フロントは2名。そのうち1人が、受付と予約管理を全般的に担当している。
  - **理由**:手順が少なければ、受付をしながら、ウォークインの入力も同時に進められる。これから案内する部屋に、予約が入ってしまうことを防げる。そのため、フロントが1人でも回しやすくなる。
- **環境**:フロントのタブレットまたはPCで予約管理をしている。
  - **理由**:今のシステムは、部屋番号の小さなボタンを押して人数と時間を入れないと登録できない。フリータイムのプランを選んでも2時間で入力されるなど、細かく面倒な操作が多く、受付をしながらさっと入力するのには向かない。このアプリでは、入れたい時間帯のタイムテーブルをタップするだけで仮のウォークインを入れられる。受付が落ち着いたら、そのウォークインをタップして、人数や時間を編集できる。

### 4-2. 自分とユーザーの距離
 
**自分自身**
 
私自身が、実際に現場で予約システムを使っているから。課題を毎日体験している当事者として、使う側の目線でアプリを作れる。
 
### 4-3. 実際に使われる可能性について
 
- **最初に使ってくれそうな人**:同じ店の店長。「楽になった」と言ってもらえる場面を想像している。

- **思い出す場面**:繁忙時間帯は、受付のたびにこのアプリを思い出し、使う。

- **代わりに使っているもの**:今の予約システム。電話予約は、いったんメモに書き留めている。

- **置き換える理由**:今のシステムは入力が細かく、受付をしながら操作しづらい。このアプリは、時間帯をタップするだけで仮のウォークインを入れられ、落ち着いてから人数や時間を編集できる。受付と入力を同時に進められるので、予約の重複を防げる。さらに、欲しい人数の部屋だけ予約を取れるようにもできる。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ
 
- **きっかけ**:もっと回転率を上げて、売り上げを伸ばすために必要だと感じたとき。

- **最初の一歩**:店舗情報、部屋、プラン(時間の幅や時間帯)を登録する。

- **使い続ける理由**:
  - **習慣**:受付のたびに入力する。
  - **必要性**:売り上げを伸ばすために使う。
  - **価値**:予約管理の手順が少ないので、他の業務に集中する時間が生まれる。
- **乗り換えのハードル**:基本的な操作は今のシステムとほとんど変わらない。ただ、小さいボタンの操作に慣れていた人は、最初だけ慣れが必要になる。それでも、1日使えば慣れると考えている。
- **機密情報への配慮**:予約に必要な氏名と電話番号だけを登録し、入力項目は最小限にする。来店済みになった予約の電話番号は、パスワードのように「●●●●」で伏せて表示する。データは残るので、必要になったときの確認もできる。

### 6-1. ユーザーの変化
 
- **行動の変化**:
  - 部屋が混んできて1名の予約を断りたいとき、フロントのスタッフが、1名から取れる枠を、簡単に2名以上に変更できる。
  - 受付が終わってから来店入力をしていたのが、受付をしながらでも入力できるようになる。

### 6-2. 価値を一文で表す
 
このサービスは、繁忙時にフロントを回すスタッフが、受付をしながら予約を管理し、欲しい人数の予約を取って売り上げを伸ばせるようになるサービス。

## 8. このアプリの懸念点とその対策
 
### 懸念点①:変更した定員を、元に戻し忘れる
 
- **何が問題になりそうか**:部屋名を押して定員を変えられるようにするが、変更した定員を元に戻し忘れる。
- **なぜそう思うか**:繁忙時は手が回らず、落ち着いてから戻す作業が後回しになりやすいから。
- **そのために考えている対策**:営業時間が終わったら、変更した定員が自動で元の設定に戻るようにする。本リリースでは、いつまでその設定を保存するかを選べるようにする。

### 懸念点②:実際の空席と予約がズレる
 
- **何が問題になりそうか**:実際には空いていないのに、予約が取れてしまう。たとえば、13:00から予約や来店で満室なのに、1名のフリータイムが取れてしまう。
- **なぜそう思うか**:予約を、実際の空席と紐づけて受け付けられるか、まだ分からないから。ズレると、予約の重複を減らすという、このアプリの良さが薄れてしまう。
- **そのために考えている対策**:
  - 予約フォームで人数を入力すると、その人数で案内できる部屋が空いている時間とプランだけを表示する。空きがなければプランを表示せず予約できないようにするか、最短で空いている時間の枠を表示する。(例:13:00の昼フリータイムは1名だと選べず、2名に変えると表示される)
  - 店舗で設定したプランの時間の範囲を確認し、他の予約・ウォークイン・ブロックと重複がなければ、予約を受け付ける。
  - 重複しているものはタイムテーブル上にも表示し、この重複確認を、予約を受け付けるかどうかの判定にも使う。

## 9. 今後の展開・発展の方向性
 
### 今考えている発展案
 
**機能追加の方向性**
 
- **混雑する時間帯の確認**:予約データから、一番予約が混み合う時間が分かる。その時間の人員を多めにするなど、無駄のない運営ができる。
- **売り上げ予測**:来店前の予約の売り上げ予測を表示する。POSの売り上げと合わせて、予算達成まであといくらかを、確認しやすくなる。
- **プランの料金**:売り上げ予測のために、プランごとの料金を持たせる。

- データが溜まるほど予測しやすくなり、売り上げを伸ばすための、店側の施策も打ちやすくなる。

## 10. 技術スタック(手段としての技術)
 
### 10-1. 使用予定の技術
 
- **フレームワーク**:Ruby on Rails 8.1.4(Ruby 3.4.12)
- **DB**:MySQL
- **デプロイ先**:AWS
- **開発環境**:Docker
- **使用予定ライブラリ**:
  - 画面まわり:turbo-rails、stimulus-rails(Hotwire)、jsbundling-rails
  - ログイン:bcrypt(パスワードの暗号化)
  - テスト:capybara、selenium-webdriver
  - 品質・セキュリティ:rubocop-rails-omakase(コードの書き方のチェック)、brakeman(脆弱性チェック)、bundler-audit(gemの脆弱性チェック)
  - ※開発が進んで増えたら、随時追記する

### 10-2. 技術選定の比較検討
 
| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Ruby on Rails | 採用 | 一番理解が深く、MVPを最も作りやすいと感じたため |
| React + TypeScript | MVPでは不採用(本リリースで導入予定) | 導入したいが、MVPの期限内では、理解が追いつかないリスクがあるため |
 
- **今回チャレンジしたい点**:Hotwire(TurboとStimulus)を使って、受付をしながらでも、さっと入力できる操作感を作る。React + TypeScriptは、本リリースでチャレンジする。
- **不安な点**:時間がない中で、MVPのリリースを期限内に、自分がイメージしているところまで作れるかが不安。

### 10-3. キャッチアップ不足の懸念
 
Reactは、MVPのリリース後に、React単体のキャッチアップと、アプリに組み込む技術的な検証を行ったうえで、導入する方針です。
